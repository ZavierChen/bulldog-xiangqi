# 算法与实现边界

斗牛犬是本地视觉连接与搜索调度程序。底层走法搜索、剪枝、置换表和 NNUE 评估来自 Pikafish；以下是应用层实现。

## 1. 从图像到可信历史

识别器先在已支持皮肤中匹配棋盘边框，缓存定位并复核窗口尺寸。将棋盘映射到 9×10 交叉点，结合圆形检测与 15 类 CNN（空格、红黑各七类棋子）批量分类。识别可使用 DirectML，CPU 提供回退；GPU 不参与 Pikafish 搜索。

分类结果要经过棋子数量、局面变化和引擎合法走法校验。吃子动画、选中高亮、遮挡等临时画面不能直接写入历史。已建立历史时，用上一局面所有合法走法生成预期棋盘，与新画面匹配；确认一步后切换走棋方，无需每帧重新依赖头像判断。

静态中局无法总是唯一推断谁走棋。无头像保底用下方棋色确定本方，再由用户选择“我方先手 / 对方先手”。无法确认变化时等待或重连，不把点击成功等同于已经走成。

对应代码：`vision.py`、`board_bootstrap.py`、`tracker.py`、`controller.py`。以下模块路径均相对 `connector/bridge/`。

### 两点定位与皮肤学习

手动定位将所选窗口截图中的两个对角交叉点保存为内容区域的归一化比例，排除显著的左右黑边。横向按 8 个间隔、纵向按 9 个间隔计算 90 个中心；截图处理和落子都使用同一组坐标变换。窗口平移后，屏幕原点通过当前窗口矩形重新获得，不依赖某个皮肤的棋盘边框模板。窗口内布局显著改变仍需用户检查网格；旧格式标定在长宽比漂移时拒绝点击并保留上下文。

棋盘被仿射归一化到固定网格后，圆检测用于确定占用位置。将占用集合与标准开局及引擎生成的全部合法红方首着后的集合比较；只有唯一匹配时，才把这些位置作为带标签的皮肤样本。下方棋色由文字颜色判断，也可手动指定，因而红方已走一步、黑方位于下方时仍可学习。没有唯一匹配不强行归类成开局。

外观特征结合去均值灰度、边缘和红绿差；匹配时使用圆形中心掩码，降低对抗锯齿敏感的边缘权重，并批量尝试归一化图像上正负三像素的位移。字色只统计棋子中心，避免金色边缘、红色高亮干扰。向量归一化后通过自有的两操作 ONNX 图（Transpose + MatMul）在 DirectML 上计算相似度。比较不同棋种之间的分数差，过滤模糊分类。这个小模型没有训练权重。

只有唯一开局匹配或用户明确确认的标签才持久保存为压缩特征库；普通中局猜测不会自动写入库。每份文件仅含特征与标签，原子写入，无 pickle；加载检查维度、标签与数值，最多检查最近 32 份。中局按多棋子匹配率与相似度中位数选择皮肤，断线与新局均保留现有样本，跨进程可重新加载。第一次碰到遮挡导致匹配失败时会限频重试，不把失败永久记成无皮肤。

中局可复用已有棋子 CNN；不确定的文字补充调用本地 PP-OCRv4 识别模型，按简繁棋字映射为棋种，结合颜色与将帅/子力约束核对。OCR 不是任意字体保证：部分艺术字会拒识，可手动校正并续接。GPU 负责模型推理和外观向量匹配，窗口定位、几何处理和规则核验仍使用 CPU。

双帧既要求识别棋盘一致，也检查棋子主体的归一化灰度变化，忽略背景粒子和外圈高亮。无法确认时不更新可信棋盘，也不清除皮肤库、历史和搜索结果。手动校正会暂停连接，在沙盒修改棋子及当前走棋方；确认后核对占用位置和画面稳定性，学习确认样本，再恢复连接。局面未变或命中已知合法路径时保留原 Tracker 与分析，否则重建当前局面；不会把无法解释的历史当成已确认。

已有可信历史时，少量拒识还可由合法走法补全：至少约九成已识别标签完全一致、占用位置完全一致，且当前局面、待确认本方着法或下一步合法变化中只有一个完整棋盘吻合，才补上未知标签。不覆盖已识别的矛盾标签，也不从整盘未知图像猜棋。候选按完整历史与待确认着法缓存，只有需要补全时才生成，不额外搜索评分。手动编辑期间对方走完一步时，双帧均能读准且唯一对应所选方一步合法走法，确认时可顺势推进。

两点模式以本方先走作临时假设，但优先采用已有且一致的合法历史。首次试走未被确认时不写入历史；如果随后出现对方的一步合法变化，以该步重建正确回合并清除未生效的试走，保留可以继续用的分析结果。

对应代码：`manual_picker.py`、`manual_grid.py`、`manual_vision.py`、`piece_ocr.py`、`skin_store.py`、`visual_stability.py`。

## 2. 多分支后台预判

本方落子后，独立引擎在对手回合执行 MultiPV，覆盖用户选定的 2–5 个对手候选。每条 PV 的第一步是对手可能走法，第二步是本方预期回复。MultiPV 在多条根分支之间分配搜索，并不意味着每条分支获得相同节点数。

只有同一深度的所有候选到齐、各有至少两步 PV 时，才发布一个完整快照，避免将不同深度的旧结果拼起来。

经济预判从 `ponder-tuning.json` 读取默认软预算 2 秒、上限 8 秒、评分容差 25 cp。实际软预算不超过当前基础预算；硬预算按基础预算的两倍和配置上限共同限制。这些是调度启发式，不是普适最优时长。

稳定判据包括：深度至少 12；候选集合不变（允许名次交换）；至少三个不同深度覆盖稳定窗口；评分类型一致、变化不超容差。每个分支单独检查本方回复是否相同。最优对手候选的回复稳定时可以暂停，但只有各自通过检查的分支能用于快速回复。到达硬预算也暂停，同一根局面不会无休止重启。

对应代码：`pondering.py`、`ponder_policy.py`。

## 3. 命中、继续搜索与缓存约束

实际应手必须与预判中的完整历史前缀一致，且由走法重放得到的棋盘和走棋方与当前状态完全相同，才接受预判结果。快速回复仍须经过合法性和防循环过滤。局面更新会清除不再对应的提示。

若需要继续计算，停止后台搜索后将其进程提升到前台，继续使用已经建立的置换表；原前台进程留作下次后台搜索。进程常驻，线程数只在设置改变时更新。后台进程使用 Windows BelowNormal 优先级，前台恢复 Normal。

已有开局缓存、上一主变化和当前计划也会匹配完整局面与历史。它们不是无条件照搬下一步。公开版本不附带本机生成的开局缓存，缺少缓存时回退至搜索。

对应代码：`pondering.py`、`tracker.py`。

### 失焦期间保留计算

失焦、窗口移动或临时遮挡仅停止正在运行的后台搜索，不清除根局面、完整 MultiPV 快照、稳定窗口状态、已用计算预算或常驻进程。恢复同一完整历史时，在原置换表上继续分析，软/硬预算只累计实际搜索时间，不把失焦等待算成思考。

重新同步首先尝试沿用原 Tracker。相同局面保留已算着法及其评分；已知主变化或后台分支与实际棋盘唯一对应时，逐步验证合法性后推进原历史，允许恢复最多八个已搜索半回合。稳定分支可继续提供下一步；未稳定的分支只保留历史与置换表，不无条件秒走。多个路径产生歧义或无法匹配时，保留旧上下文暂停落子，等待稳定画面或手动确认；不会仅因几次失败就把中局重建成无历史的局面。明确回到标准开局时可创建新局。所有复用着法仍经过合法性与防循环过滤。

真正进入下一局、用户明确重新指定先手或关闭程序时才清理对应上下文。缓存不写入公开数据，也不跨进程保存引擎置换表。

## 4. 前台时间分配

基本完整的开局前 20 个半回合保持基础时间；若接入的是子力已明显减少的中局，则不机械套用开局保护。

对不同本方局面收集评分，连续三次不占优后，按近期评分中位数分级，目标倍率为 1.25、1.5、2 或 3。倍率逐步变化，预算最多 30 秒；连续回稳后逐步降低。加时需要真实细化搜索，不用缓存直接跳过。尚未读取外部平台剩余时钟，因此用户需要按对局时限设置基础秒数。

对应代码：`thinking_budget.py`。cp 为引擎的兵值百分单位；杀棋分另行处理。

## 5. 沙盒前三候选与局面估计

用户摆好局面并点击提示后才启动计算。先检查将帅、子力数量、限定落点与走棋方可行性，防止把明显无效的 FEN 发送给原生引擎；这些检查不能证明任意自摆局面都可从标准开局到达。

一次 `go movetime` 配合 MultiPV=3 获取候选。只使用同一深度、互不重复、合法且不带上下界标记的完整结果；不足三个合法走法时显示实际数量。按当前走棋方评分排序，杀棋和普通评分分开比较。三条箭头表示同一手的替代选择，不是后续连续三步。

胜/和/负直接读取引擎 `UCI_ShowWDL` 输出，转换红黑视角显示，不为显示另开搜索。胜率是模型估计，不是实战胜率统计。没有有效 WDL 就显示暂无。

编辑棋盘时递增版本、发送停止请求并清除提示。工作线程返回的版本若已过期则丢弃。连接运行时不启动沙盒搜索，空闲界面不持续计算。

对应代码：`sandbox.py`、`sandbox_model.py`、`board_view.py`、`position_analysis.py`。

## 6. 循环与界面恢复

记录带走棋方的历史局面，并过滤重新进入历史局面的候选，另保留重复将军检查。这能保守减少长将、长捉循环，但不是完整亚洲棋规判定：可能放弃合法重复和棋，也不能保证识别所有平台的追捉规则。没有可接受候选时停止自动落子。

正常识别循环不每次扫描完整广告链。连续识别失败后进入“关闭广告 → 可选升级提示 → 继续对局”状态流程；低概率兼容探测按较长超时触发。每次操作前重新检查窗口和目标，窗口移动后重新定位。它依赖已适配的界面特征，不能保证识别任意广告或游戏皮肤。

“积分加速”是这条恢复链中的可选遮挡，可出现在广告、升级或续局阶段。先定位浅色卡片并归一化尺寸，再同时匹配上方固定标题与右上角关闭控件，额外确认红色叉号。只在双帧位置一致、点击前新截图仍匹配且窗口未移动时关闭；任一帧提示存在但不稳定时，暂停后方续局点击。该检查不在正常棋盘循环运行，完整测试截图留在本地，仓库仅保留标题和关闭控件的小模板。

叠层界面先关闭最上层广告，再检查后方可选弹窗。广告关闭匹配只使用叉号的中心区域，避免半透明外圈随背景变化导致失配；用 SDK 标记和卡片边界限制按钮位置。标记被素材背景干扰时，仅对已支持的“16:9 素材 + 白色操作底栏”布局启用几何后备，并要求底栏具有宽绿色操作按钮。小尺寸图标额外尝试相邻像素尺寸，保持 0.94 的相似度门槛。双帧确认和点击前复核仍然保留。

对应代码：`tracker.py`、`screen_flow.py`、`ads.py`、`popups.py`、`end_screens.py`。

## 验证与数据

仓库保留可重复的状态、引擎与界面测试，运行 `python -m unittest discover -s tests -v`。原始截图、实战历史、日志、个人设置、测速样本和开发备份仅在本地归档，不作为公开实验数据。单元测试通过与用户实际界面兼容是两件事；已有皮肤之外需额外适配。
